# PRD: Account Entries Period Report

**Status:** Draft
**Date:** 2026-06-23
**Author:** thimmaiah

---

## Problem

`AccountEntry` records are generated by `AllocationRun`s for a fund over a period, but there is no analytical view of what was generated. Today the only ways to inspect entries for a period are the raw grid (`/account_entries?filter=true`), the `AccountEntryPivot` table, and ad-hoc charts embedded in widgets (`AccountEntryChartsHelper`). None of these answer "what happened in this fund/folio for this period, and how does it compare to before" in one place. Fund managers reviewing a quarter-end run, or answering an investor's question about their folio, have to manually filter the grid and reconcile numbers themselves.

## Goal

A report, viewable in-app, that summarizes `AccountEntry` activity for a date range at two levels:

1. **Fund-level** — aggregate view across all folios (+ fund-only entries) in a fund for the period.
2. **Folio-level** — drill-down for a single `CapitalCommitment` ("folio") for the period.

Both levels show breakdowns by entry name/type, trailing-period trend context, and a detail table to drill into the underlying entries. No PDF/export in this iteration — interactive view only.

---

## Concepts

### Scope resolution
The report is keyed by **fund + date range**, not by a single `AllocationRun` id, because multiple `AllocationRun`s can target the same `reporting_date` (re-runs, or separate runs per fund_formula/template). A range is needed because a report should be runnable from two entry points:

| Entry point | How the range is derived |
|---|---|
| From an `AllocationRun` | `start_date` = run's `start_date`, `end_date` = run's `end_date`. The run merely pre-fills the picker. |
| Ad-hoc, from the fund | User picks `start_date`/`end_date` directly (defaulting to the latest `reporting_date` present, single day). |

Underlying query in both cases:
```ruby
fund.account_entries.where(reporting_date: start_date..end_date)
```
The `AllocationRun` that produced any given entry remains visible as provenance (entry's `allocation_run_id`) but is never the lookup key.

### Fund-level vs folio-level
- **Fund-level**: `fund.account_entries.where(reporting_date: range)` — all folios combined, plus fund-only entries (`capital_commitment_id IS NULL`, e.g. fund-level fees before allocation).
- **Folio-level**: same query further scoped to one `capital_commitment_id`. Single-folio drill-down only (not a side-by-side multi-folio grid — that already exists as the pivot/grid view).

## User Stories

| # | As a… | I want to… | So that… |
|---|-------|-----------|----------|
| 1 | fund manager | open a report directly from an `AllocationRun` after it completes | I can sanity-check what the run generated without leaving the run's context |
| 2 | fund manager | open a report for a fund by picking any date range | I can review periods that weren't run via the allocation engine (imports, adjustments) too |
| 3 | fund manager | see entries broken down by name/entry_type with totals | I understand the composition of the period (fees vs distributions vs capital calls) |
| 4 | fund manager | see a trailing-period trend for each entry type | I can tell if this period is in line with history or an outlier |
| 5 | fund manager | drill from the fund-level report into one folio | I can answer an investor's question about their specific entries without re-filtering the grid |
| 6 | investor (limited access) | view their own folio's report for a period | I get a readable summary instead of a raw transaction list |
| 7 | fund manager | click through from any summary number to the underlying entries | I can verify a total against source records |

## Functional Requirements

### FR-1: Entry points
- **From AllocationRun show page**: a "View Report" button/link passing `fund_id`, `start_date`, `end_date` (run's own dates).
- **From Fund page / standalone**: a report picker (fund selector + date range) that lands on the same fund-level report.
- Both routes resolve to the same controller action; the `AllocationRun` is not stored on the report, only used to seed params.

### FR-2: Fund-level report
Sections, top to bottom:
1. **Header** — fund name, date range, total entry count, total net amount, link to the underlying `AllocationRun`(s) for that range (`AllocationRun.where(fund:, end_date: ...)`) if any exist.
2. **Summary KPIs** — total amount by high-level direction (sum of positive vs negative `amount_cents`), entry count, distinct folios touched, distinct entry names.
3. **Breakdown by entry name/type** — pie or bar chart of total amount grouped by `name` (reuse `AccountEntryChartsHelper#account_entries_chart` with `aggregate_by: 'sum'`), restricted to `use_entries: 'folio_only'` vs `'fund_only'` as a toggle.
4. **Trailing-period trend** — for the top N entry names by absolute amount, a time-series chart over the trailing 4–8 periods leading up to `end_date` (reuse the existing quarter/month aggregation logic in `AccountEntryChartsHelper`).
5. **Top folios** — table of top 10–20 folios by absolute amount for the period, each row linking to that folio's drill-down report (FR-3) with the same date range.
6. **Detail table** — paginated entry list for the range, reusing `AccountEntryPivot`'s pluck-based pagination (never instantiate full `AccountEntry` objects for a fund-wide range — partitioned table, can be large).

### FR-3: Folio-level report
Same shape as fund-level, scoped to one `capital_commitment_id`:
1. **Header** — investor name, folio_id, fund, date range.
2. **Summary KPIs** — total amount, entry count for this folio in the range.
3. **Breakdown by entry name/type** — chart, scoped to this folio.
4. **Trailing-period trend** — same trailing-period logic, scoped to this folio.
5. **Detail table** — every entry for this folio in the range (folio-scale data, safe to load directly without the pivot pagination machinery).
6. Back-link to the fund-level report for the same date range.

### FR-4: Navigation/drill-down
- Fund-level "Top folios" rows link to `folio report` with the same `start_date`/`end_date` carried over.
- Folio-level report links back to its fund-level report.
- Both report views accept the date range as URL params so they're shareable/bookmarkable within the app.

### FR-5: AI commentary per section
Each section in FR-2/FR-3 (Summary KPIs, Breakdown, Trailing-period trend, Top folios — the last only at fund level) gets its own AI-generated narrative, following the precedent set by `AccountEntryExplainerService`/`AccountEntryExplainJob` (per-record async explanation) and `AiReportSection` (per-section cached content on a parent record).

- **Trigger**: a section's commentary job auto-fires the first time that section is rendered for a given scope+range if no commentary exists yet for the current data fingerprint (see Invalidation below). A "Regenerate" button is always available to re-run it on demand, even when current commentary is already fresh.
- **Content depth**: descriptive narrative of what the section's numbers show, **plus explicit anomaly flagging** against trailing-period history — e.g. "Management Fee is 42% above its trailing 4-quarter average of $X." This means the commentary step needs the same trailing-period series used for the Trend chart (FR-2 item 4) as input, not just the section's own current-period numbers.
- **Invalidation**: a fingerprint (count + `sum(amount_cents)`, optionally a digest of distinct `name`s present) is computed for the section's underlying query each time the report is viewed. If the stored fingerprint on the cached insight doesn't match, the commentary is marked stale and regenerated automatically (same trigger path as "no commentary yet") rather than silently shown against changed numbers — this matters because a new `AllocationRun` can re-run and change entries for a `reporting_date` that's already been reported on.
- **Audience/tone**: mirrors `AccountEntryExplainerService` — financially literate fund managers/finance ops, no implementation jargon, monetary values always shown with their currency equivalent.

#### Data model: `AccountEntryReportInsight`
A new lightweight, cache-like model (not a "report" record in itself — there is still no persisted top-level report):

```
account_entry_report_insights
  id
  entity_id            FK -> entities, NOT NULL
  fund_id              FK -> funds, NOT NULL
  capital_commitment_id FK -> capital_commitments (nullable; null = fund-level scope)
  start_date           date, NOT NULL
  end_date             date, NOT NULL
  section_key          string, NOT NULL   (summary_kpis | breakdown | trend)
  status               string             (pending | generating | complete | error | stale)
  content              json               (narrative text + structured anomaly list)
  data_fingerprint     string             (hash of count + sum(amount_cents) [+ distinct names] for the section's query)
  generated_at         datetime
  generated_by_id      FK -> users (nullable; null when auto-triggered)

  INDEX (fund_id, capital_commitment_id, start_date, end_date, section_key) UNIQUE
```

#### Generation flow
- New job, e.g. `AccountEntryReportCommentaryJob`, mirroring `AccountEntryExplainJob`'s structure: loads the scope, recomputes the relevant aggregates (reusing the same service methods as the section itself — never re-deriving logic in the prompt builder), calls `LlmService.ruby_llm_chat(entity:)`, parses a JSON response (`narrative`, `anomalies: [{ metric, current_value, trailing_average, deviation_pct, note }]`), and writes it to the `AccountEntryReportInsight` row (status `complete`/`error`) with the fingerprint computed at generation time.
- New service, e.g. `AccountEntryReportCommentaryService`, mirroring `AccountEntryExplainerService`'s structured-prompt approach (explicit numbered inputs, strict "only describe what's in the data provided" instruction, JSON-only output contract).
- Failure handling, locking pattern, and user notification on completion should follow `AccountEntryExplainJob` exactly (graceful `RecordNotFound` discard, `with_lock` read-modify-write, `UserAlert`-style notification linking back to the report).

### FR-6: Permissions
- Fund-level report: visible to employees with fund access (mirrors `AccountEntryPolicy#index?` — `user.enable_funds && user.curr_role != 'investor'`).
- Folio-level report: visible to employees with fund access, **and** to the investor who owns that `capital_commitment` (mirrors `AccountEntryPolicy#show?` — `permissioned_employee? || permissioned_investor?`).
- The existing `AccountEntryPolicy#report?` method currently aliases to `update?` — that's wrong for a read-only report and should not be reused as-is. New policy methods (e.g. `fund_report?`, `folio_report?`) are needed rather than overloading `report?`.
- AI commentary generation (FR-5) follows the same visibility as the section it belongs to — no separate write permission. An investor viewing their own folio report can trigger/regenerate that folio's commentary; they cannot trigger fund-level commentary they aren't permissioned to view.

## Data / Query Layer

The report itself remains computed on request — no persisted "report" record. The only new persisted model is `AccountEntryReportInsight` (FR-5), which caches AI commentary, not report data:

- New service object(s), e.g. `AccountEntryReport` (fund-level) and reuse/extend for folio-level (scoped variant), responsible for:
  - Resolving the `reporting_date` range query.
  - Producing summary KPIs via `group(...).sum(:amount_cents)` — never loading individual records for aggregates.
  - Producing trailing-period series by delegating to the same grouping logic already in `AccountEntryChartsHelper`/`AccountEntryTimeSeries` rather than re-implementing it.
  - Producing the "top folios" ranking via a single grouped/ordered query (`group(:capital_commitment_id).sum(:amount_cents)`, then loading just those `CapitalCommitment` rows).
- Detail table at fund level reuses `AccountEntryPivot`'s pluck-based, metadata-first pagination (see `account_entry_pivot.md`) given the table is partitioned by year and fund-wide ranges can be large. Folio-level detail table can load `AccountEntry` records directly — bounded by one folio.

## New Artifacts (expected)

- `AccountEntryReportsController` (or similar) with `fund` and `folio` actions, both accepting `fund_id`/`capital_commitment_id` + `start_date`/`end_date`.

- `AccountEntryReportInsight` model + migration (FR-5).
- `AccountEntryReportCommentaryJob` + `AccountEntryReportCommentaryService` (FR-5).
- A `generate_commentary`/`regenerate_commentary` controller action (or nested route) per section, used by both the auto-trigger and the manual "Regenerate" button.

## Out of Scope (this iteration)
- PDF/DOCX export (the `*_doc_generator.rb` + Sablon pattern is the natural extension later if LP-facing distribution is needed).
- XLSX export of the report data.
- Scheduling/notification (the generic `Report`/`ReportSchedule` models are a separate concern; this report is not registered in `Report.reports_for` for MVP).
- Side-by-side multi-folio comparison report (the existing pivot/grid already covers that need).
- Budget/forecast variance (comparing actual entries to a planned figure) — trailing-period trend only, no forecast data source exists today.

## Open Questions
- What counts as "top N" for the trailing-period trend — top by absolute amount in the current period, or a fixed/configurable list of entry names per fund?
- Should fund-only entries (`capital_commitment_id IS NULL`) be included in folio-level reports' fund context, or strictly excluded since they don't belong to any folio?
- Trailing period length (4 vs 8) — fixed or user-adjustable on the report screen?
